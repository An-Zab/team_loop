# team_loop

## Суть проекта (в 3 предложениях)

1. Это автономный цикл выполнения задач для локального агентского движка Strata:
   **Аналитик → Исполнитель ↔ Изолированный Ревьюер**.
2. Ревьюер изолирован: он не видит историю метаний и оправданий Исполнителя, а
   получает цель шага, его отчёт и результат машинной проверки файлов, поэтому
   вердикт опирается на факты, а не на самомнение модели.
3. Если контекст локальной модели переполняется, работа сохраняется в `handoff.md`
   и продолжается в новом чате (механизм Handoff).

План работ — в [PLAN.md](PLAN.md); здесь реализованы **ШАГИ 1–6**.

Запускать проект удобнее через точку входа Шага 6: `python run_strata_team.py "Текст
задачи"` (подробности — в разделе «ШАГ 6» ниже).

## ШАГ 2 — `isolated_reviewer.py`

Изолированный Ревьюер проверяет один шаг плана и выносит вердикт
**ПРИНЯТО / ДОРАБОТАТЬ**. Сначала работает машина, потом модель:

* `run_objective_checks(file_paths)` — проверяет, что файлы реально лежат на диске,
  и для каждого `.py` запускает проверку синтаксиса отдельным процессом Python
  (`sys.executable -m py_compile`). Возвращает текст: либо точную фразу
  `Синтаксис всех файлов корректен`, либо список проблем с точным `stderr`
  компилятора.
* `review_step(step_goal, executor_report, modified_files=None)` — возвращает словарь
  `{"accepted": bool, "feedback": str, "review_tokens": int}`.

Как Ревьюер решает (важно для понимания результатов):

| Ситуация | Вызов модели | `accepted` | Текст в `feedback` |
| --- | --- | --- | --- |
| В `.py` синтаксическая ошибка | **нет** | `False` | `Ошибка компиляции Python:` и точный `stderr` |
| Указанного файла нет на диске | **нет** | `False` | «файлы не найдены на диске» |
| Файл не проверить (нет прав, файл занят, таймаут) | **нет** | `False` | «Не удалось проверить синтаксис Python» — это проблема окружения, а не кода |
| Синтаксис чист, модель ответила | да, `temperature=0.0` | `True` при `ПРИНЯТО`, `False` при `ДОРАБОТАТЬ` | полный ответ ревьюера |
| Модель не ответила (сервер выключен, таймаут) | попытка | `False` | `Проверка модели не выполнена:` и что проверить |
| Модель нарушила формат первой строки | да | `False` | полный ответ ревьюера + пояснение |

Небезопасный вариант «не ответила — значит принято» сознательно не используется:
лучше вернуть шаг на доработку, чем принять непроверенную работу.

Изоляция реализована буквально: в запрос уходят **ровно два сообщения** (`system`
и `user`) и три блока в `user` — «Цель текущего шага», «Отчет/код исполнителя»,
«Результат объективной проверки файлов». История основного чата Исполнителя сюда
не передаётся никогда, второй инстанс модели в памяти не поднимается — запрос идёт
на тот же локальный сервер.

Объём исходного текста в блоках ограничен: цель — 6000 символов, отчёт Исполнителя —
12000, объективная проверка — 4000. При обрезке отчёта сохраняются начало и конец
(включая итог и результаты тестов); в промпт добавляется пометка об обрезке.

Запрос к модели сделан на стандартной библиотеке (`urllib`), поэтому новых
зависимостей ставить не нужно. Адрес и имя модели берутся из Шага 1
(`OPENAI_BASE_URL`, `OPENAI_API_KEY`, `MODEL_NAME`).

Проверка из любой папки (модуль сам находит `team_config.py`):

```powershell
python F:\Projects\team_loop\isolated_reviewer.py
```

## ШАГ 3 — `handoff_manager.py`

Менеджер Handoff сохраняет состояние работы, когда контекст локальной модели почти
заполнен, и возвращает его в новый чат с пустой историей.

* `generate_handoff(task, plan, current_step_idx, recent_messages, blocker_reason)` —
  просит модель сжать контекст и записывает результат в `handoff.md` (UTF-8).
  Возвращает записанный текст или `None`, если записать не удалось (тогда в консоли
  уже напечатана причина по-русски).
* `load_handoff_if_exists()` — если `handoff.md` читаемый и содержит четыре непустых
  раздела шаблона, читает его и переносит в `handoff.bak`; при явном `--resume` пустой,
  нечитаемый или неполный основной файл не затирает пригодную резервную копию, а
  загрузчик использует `handoff.bak`. Обычный запуск по-прежнему не подхватывает
  резервную копию автоматически.

Шаблон `handoff.md` — ровно четыре раздела (требование ТЗ):

| Раздел | Что в нём |
| --- | --- |
| `# Исходная задача` | текст задачи полностью, без потерь и без обрезки в файле |
| `# Статус плана` | все шаги: выполненные `[x]`, текущий и оставшиеся `[ ]` |
| `# Артефакты и файлы на диске` | какие файлы созданы/изменены и что в них, без копирования кода |
| `# Текущий контекст и блокер` | на каком шаге остановились, замечания ревьюера или причина, что делать первым |

Как это работает (важно для понимания результатов):

| Ситуация | Что происходит |
| --- | --- |
| Модель ответила по шаблону | её текст очищается от вступлений и блоков ` ``` ` и пишется в `handoff.md` |
| Модель сократила или пересказала задачу | раздел `# Исходная задача` заменяется полным исходным текстом, в файле — пометка «исправлен программой автоматически» |
| Модель исказила отметки `[x]`/`[ ]`, пропустила или придумала шаг | раздел `# Статус плана` пересобирается из настоящего плана и номера текущего шага |
| Модель пропустила часть разделов | пропущенные разделы дописываются из реальных данных, в консоли — предупреждение |
| Модель не ответила (сервер выключен, таймаут) | `handoff.md` всё равно создаётся из реальных данных: задача, план с отметками, блокер, хвост переписки |
| `handoff.md` пустой, нечитаемый или неполный (не все четыре раздела шаблона) | он не переносится поверх `handoff.bak`; при `--resume` используется пригодная резервная копия, если она есть. Обычный запуск игнорирует непригодный файл и работает по переданной задаче |
| `handoff.md` сохранён не в UTF-8 | читается как CP1251 с предупреждением; работу это не останавливает |
| Файл `handoff.bak` открыт в Блокноте | переименование не удаётся, `handoff.md` остаётся на диске, текст всё равно передаётся в работу |

Ответ модели не принимается на веру: непустой раздел ещё не значит достоверный. Перед
записью в файл программа сверяет его с тем, что знает точно — с дословным текстом
задачи и с планом, отметки `[x]`/`[ ]` в котором выводятся из номера текущего шага.
Сокращённую или пересказанную задачу, пропущенный шаг и отмеченный выполненным текущий
шаг программа подменяет достоверными данными и помечает раздел фразой «исправлен
программой автоматически». Честный ответ модели не трогается вообще, а каждое
исправление печатается в `stderr`.

Запасной режим — сознательное решение: потеря точки продолжения работы хуже, чем файл,
где часть текста собрана программой, а не моделью. Такой файл помечен фразой
«собрана программой автоматически».

История чата в промпт попадает не целиком, а только последние 12 сообщений и каждый
текст обрезается до 1500 символов: запрос на сжатие идёт в ту же модель с тем же
окном контекста и не должен переполнить его самостоятельно. Обрезка по `MAX_TASK_CHARS`
(6000 символов) касается **только промпта**: в `handoff.md` текст задачи пишется
целиком. Файл — единственное место, где требования сохраняются, и обрезать его значит
потерять часть задачи безвозвратно.

Запрос к модели — на стандартной библиотеке (`urllib`), новых зависимостей ставить
не нужно. Адрес и имя модели берутся из Шага 1.

Запуск демонстрации из любой папки (модуль сам находит `team_config.py`):

```powershell
python F:\Projects\team_loop\handoff_manager.py
```

## ШАГ 4 — `analyst_planner.py`

Аналитик превращает задачу пользователя или пригодный handoff в список шагов,
который потом по очереди выполняет главный цикл. При явном `--resume` пригодный
`handoff.bak` используется, если основной `handoff.md` отсутствует или непригоден.

* `build_execution_plan(user_task="", *, resume_backup=False)` — возвращает кортеж
  `(список_шагов, текст_handoff_или_None, потраченные_токены)`. Сначала вызывает
  `load_handoff_if_exists()` Шага 3: если найден пригодный handoff, модель получает
  его содержимое с задачей «Проанализируй handoff и верни список ТОЛЬКО ОСТАВШИХСЯ
  невыполненных шагов для завершения проекта»; иначе модель разбивает на шаги саму
  поставленную задачу. Аргумент `resume_backup=True` включает чтение `.bak` только
  для явного возобновления. Аргумент задачи можно оставить пустым, если доступен handoff.
* `parse_plan_steps(answer)` — парсер ответа модели: JSON-массив строк,
  объект `{"steps": [...]}`, нумерованный список (`1. ...`, `Шаг 1: ...`),
  маркированные пункты и чекбоксы (`- [ ] ...`). Снимает Markdown, кавычки и
  вступления, удаляет дубли и лишние пробелы, возвращает чистый `list[str]`.

Как Аналитик решает (важно для понимания результатов):

| Ситуация | Вызов модели | Что вернётся | Что видно в консоли |
| --- | --- | --- | --- |
| Есть пригодный handoff | да, `temperature=0.0` | только шаги с `[ ]` и текст handoff | — |
| Нет пригодного handoff, задача передана | да, `temperature=0.0` | 2–5 шагов (максимум 12) и `None` | — |
| Модель ответила `[]` при handoff | да | один контрольный шаг «сверь и заверши проект» | предупреждение |
| Модель не ответила (сервер выключен, таймаут) | попытка | один шаг с текстом задачи, токены `0` | `План не получен: ...` |
| Модель ответила прозой не по формату | да | один шаг с текстом задачи | `План не получен: ответ модели не похож...` |
| Ни задачи, ни пригодного handoff | **нет** | один шаг «уточни задачу у пользователя» | предупреждение |

Два правила, которые защищают работу:

1. **План есть всегда.** Аналитик не падает и не оставляет цикл без плана: если
   декомпозиция не получилась, шагом становится сама поставленная задача, а в
   `stderr` пишется причина на русском. Лучше выполнить работу одним шагом, чем
   остановить весь цикл.
2. **Handoff не теряется.** Пригодный основной `handoff.md` читается и переносится в
   `handoff.bak`. При явном `resume_backup=True` пригодный `.bak` подхватывается,
   если основной файл отсутствует или непригоден; резервная копия остаётся нетронутой.
   Если план построить не удалось, Аналитик восстанавливает прочитанное состояние,
   когда это безопасно, через `finally`, в том числе при непредвиденной ошибке и
   `KeyboardInterrupt`/`SystemExit`. Прерывания не подавляются и передаются вызывающему
   коду; следующая попытка может продолжить работу с сохранённого handoff.

Запрос к модели — на стандартной библиотеке (`urllib`), новых зависимостей ставить
не нужно. Адрес и имя модели берутся из Шага 1 (`OPENAI_BASE_URL`, `OPENAI_API_KEY`,
`MODEL_NAME`). В промпт попадают обрезанные по длине тексты (задача — 6000 символов,
handoff — 12000), потому что запрос Аналитика идёт в то же контекстное окно.

Запуск демонстрации из любой папки (модуль сам находит `team_config.py` и
`handoff_manager.py`):

```powershell
python F:\Projects\team_loop\analyst_planner.py
```

## ШАГ 5 — `loop_team.py`

Главный цикл команды: **Аналитик → (Исполнитель ↔ Изолированный Ревьюер)** по каждому
шагу плана, с проверкой контекста и механизмом Handoff. Здесь Шаги 1–4 начинают
работать вместе.

Прежняя версия этого файла была собрана на LangChain и LangGraph. Это прямо запрещено
правилом 1 PLAN.md («Никаких тяжёлых фреймворков»), а кроме того, пакет
`langchain_openai` на машине не установлен, поэтому старый файл падал ещё на импорте.
Теперь цикл написан на чистой стандартной библиотеке: ставить ничего не нужно,
второй инстанс модели в памяти не поднимается.

Как устроен цикл (по пунктам ТЗ):

| Этап | Что происходит |
| --- | --- |
| Старт | `build_execution_plan(task)` (ШАГ 4); если был подхвачен `handoff.md`, его краткая сводка попадает в системный контекст Исполнителя |
| Внешний цикл | `for step_idx, step_text in enumerate(plan)` — один шаг плана за раз; перед шагом запоминается `history_checkpoint` |
| 1. Проверка контекста | **перед** каждым вызовом модели: `is_context_critical(current_tokens)` → `generate_handoff(...)`, уведомление в консоль, штатная остановка |
| 2. Исполнитель | получает цель шага и `feedback` ревьюера (если попытки уже были), работает инструментами `read_file`, `write_file`, `list_files` |
| 3. Токены | после ответа обновляются через `extract_used_tokens(...)` |
| 4. Ревьюер | `review_step(цель_шага, отчёт, затронутые_файлы)` — отдельный stateless-запрос без истории основного чата |
| 5. `ПРИНЯТО` | шаг закрыт; если до этого были неудачные попытки, из истории удаляются промежуточные сообщения (Context Pruning), и цикл идёт на следующий шаг |
| 5. `ДОРАБОТАТЬ` | попытка засчитывается, замечания уходят Исполнителю, шаг повторяется |
| Попытки исчерпаны | `generate_handoff(...)` с описанием блокера и остановка выполнения |

Инструменты Исполнителя («тулзы» чтения и записи файлов):

| Инструмент | Что делает | Граница безопасности |
| --- | --- | --- |
| `read_file` | читает файл проекта | вывод обрезается до 20 000 символов |
| `write_file` | пишет файл целиком в UTF-8, создаёт нужные папки | не более 200 000 символов и дополнительно ограничено оставшимся контекстным запасом на момент запроса; только внутри проекта |
| `list_files` | перечисляет папку проекта | служебные папки (`.git`, `__pycache__`, `.venv`) пропускаются, максимум 200 записей |

Все три инструмента работают **только внутри папки проекта**: путь с `..` или на другой
диск отклоняется с русским объяснением прямо в ответе модели, а не выполняется. Именно
записанные файлы цикл передаёт Ревьюеру, поэтому вердикт опирается на реальные файлы,
а не на слова модели.

Итог запуска видно в консоли и возвращается словарём (его использует Шаг 6):

| `status` | Что значит | Код возврата |
| --- | --- | --- |
| `completed` | все шаги плана приняты ревьюером | `0` |
| `context_handoff` | контекст заполнен; код `0` возвращается только если состояние сохранено в `handoff.md` | `0` при сохранении, иначе `1` |
| `attempts_exhausted` | шаг не принят за отведённые попытки, состояние сохранено | `1` |
| `error` | непредвиденная ошибка, состояние всё равно сохранено | `1` |

Запуск (без аргументов берётся демонстрационная задача, она создаёт
`demo_palindrome.py` и `demo_palindrome_readme.md` — оба файла в `.gitignore`):

```powershell
python loop_team.py
```

Своей задачей (одной строкой):

```powershell
python loop_team.py "Создай модуль calc.py со сложением и вычитанием и файл README к нему на русском"
```

Для явного продолжения из резервной копии после прерывания используйте отдельный
флаг `--resume`. Обычный запуск и запуск с новой задачей не подхватывают старый
`handoff.bak` автоматически:

```powershell
python loop_team.py --resume
```

Перед запуском модели печатается проверка без модели: 10 строк `[OK]` про инструменты,
пути и очистку контекста. Она создаёт файлы только во временной папке Windows и не
трогает файлы проекта, поэтому её безопасно запускать посреди рабочей сессии.

Две сознательные границы, о которых нужно знать:

1. HTTP-ошибка на запросе с инструментами не считается доказательством отсутствия их
   поддержки: она может означать переполнение контекста или другую ошибку запроса.
   Цикл не принимает текстовый отчёт как подтверждение записи и повторяет попытку
   только после успешного ответа; файловый шаг без проверяемых артефактов отклоняется.
2. Между раундами вызовов инструментов оценивается контекст, включая аргументы
   инструментов при запасном подсчёте без `usage`. При приближении к порогу цикл
   сохраняет handoff и останавливается до следующего запроса.
3. Если Исполнитель зациклился на вызовах инструментов, после 8 раундов цикл сам
   запрашивает итоговый отчёт без инструментов — иначе один шаг мог бы выполняться
   бесконечно.

## ШАГ 6 — `run_strata_team.py`

Точка входа для консоли Windows: разбор параметров запуска, проверка запуска
ДО обращения к модели, печать действующих лимитов и человеческое резюме итога.
Сам цикл по-прежнему живёт в `loop_team.py` (ШАГ 5) — ничего в нём Шаг 6 не меняет,
`python loop_team.py` остаётся рабочим.

Три режима запуска (требование ТЗ):

| Команда | Что делает |
| --- | --- |
| `python run_strata_team.py "Текст задачи"` | обычный запуск цикла: Аналитик разбивает задачу на шаги, Исполнитель выполняет, Ревьюер проверяет |
| `python run_strata_team.py --resume` | продолжение работы напрямую из `handoff.md` (или резервного `handoff.bak`), текст задачи вводить не нужно |
| `python run_strata_team.py "Текст задачи" --test-handoff` | стресс-тест Handoff: порог `HANDOFF_TOKEN_LIMIT` занижается до 800 токенов |
| `python run_strata_team.py --help` | параметры запуска и готовые примеры |

Текст задачи лучше писать в кавычках одной строкой. Если кавычки забыть, слова всё
равно склеятся в одну задачу (`Создай модуль calc.py` → одна задача), но спецсимволы
PowerShell (`|`, `>`, `&`) без кавычек будут понятны оболочке, а не задаче — кавычки надёжнее.

Что печатается в консоли (требование ТЗ про логирование):

| Строка | Кто печатает |
| --- | --- |
| `Режим запуска`, `MODEL_NAME`, `MAX_CONTEXT_TOKENS`, `HANDOFF_TOKEN_LIMIT`, `MAX_STEP_ATTEMPTS`, пути `handoff.md`/`handoff.bak` | Шаг 6, до первого запроса к модели |
| `ШАГ 1 из N: <цель шага>` | Шаг 5 (цикл) |
| `Попытка 1 из 3 [Used: X / Limit: Y]` | Шаг 5 (цикл) |
| `Вердикт ревьюера: ПРИНЯТО` / `ДОРАБОТАТЬ` | Шаг 5 (цикл) |
| `ИТОГ ЗАПУСКА` и строка `Токены основного чата : [Used: X / Limit: Y]` | Шаг 6 |

Коды возврата процесса (важны, если запускать цикл по расписанию или из батника):

| Код | Значение |
| --- | --- |
| `0` | задача выполнена либо штатная остановка с сохранением `handoff.md` |
| `1` | шаг не принят ревьюером, `handoff.md` не сохранён или произошла ошибка |
| `2` | ошибка в параметрах запуска — локальная модель вообще не вызывалась |
| `130` | работа остановлена клавишей `Ctrl+C` |

Проверка механизма Handoff за минуту (критерий готовности Шага 6):

```powershell
cd F:\Projects\team_loop
python run_strata_team.py "Собери модуль calc.py со сложением и вычитанием" --test-handoff
python run_strata_team.py --resume
```

Как это работает и что важно знать:

* Порог понижается присваиванием `team_config.HANDOFF_TOKEN_LIMIT = 800` и действует
  только пока запущен процесс. Файл `.env` НЕ меняется, возвращать руками ничего
  не нужно: следующий запуск без `--test-handoff` работает обычными лимитами.
* Ожидаемое поведение теста: ровно первый шаг принят, перед вторым цикл штатно
  останавливается и сохраняет пригодный `handoff.md` (код возврата `0`). Только такой
  результат считается успешным; если Handoff сработал до первого шага или позже,
  файл не сохранился либо цикл завершил задачу без Handoff, возвращается код `1`.
* Порог 800 — это проверка реального срабатывания Handoff, а не принудительная
  команда остановки. Если выбранный сервер/шаг не приводит к указанному сценарию,
  сообщение об ошибке не следует трактовать как успешный стресс-тест.
* `--test-handoff` перезапишет существующий `handoff.md`. Точка входа предупреждает
  об этом заранее; ценное состояние лучше убрать:
  `Move-Item "handoff.md" "handoff.md.old"`.
* `--resume` и текст новой задачи не совмещаются: запуск остановится с кодом `2`,
  не потратив ни секунды работы модели.
* Если `handoff.md` уже лежит в папке проекта, обычный запуск с новой задачей
  продолжит работу ИЗ НЕГО (так устроен Аналитик, Шаг 4), и точка входа честно
  предупредит об этом и подскажет команду `Move-Item`.

Защита от частых ошибок новичка: UTF-8 консоли включается до импорта модулей, ошибки
argparse печатаются по-русски с примерами, несуществующие пути `handoff.md` проверяются
без падения, `Ctrl+C` и любая непредвиденная ошибка завершаются понятным русским
текстом вместо голого `traceback`.

## Настройка

Скопируйте `.env.example` в `.env` (`.env` в `.gitignore`) либо задайте
переменные окружения — уже установленные переменные окружения важнее файла.

| Переменная | Дефолт | Смысл |
| --- | --- | --- |
| `OPENAI_BASE_URL` | `http://localhost:1234/v1` | адрес локального OpenAI-совместимого сервера |
| `OPENAI_API_KEY` | `EMPTY` | ключ этого сервера |
| `MODEL_NAME` | `qwen-local` | имя модели |
| `MAX_CONTEXT_TOKENS` | `32768` | полный размер контекстного окна (диапазон `1..131072`) |
| `HANDOFF_FREE_RATIO` | `0.25` | долю контекста нужно оставить свободной |
| `HANDOFF_TOKEN_LIMIT` | `MAX_CONTEXT_TOKENS * (1 - RATIO)` | порог Handoff, зажимается в диапазон `1..MAX_CONTEXT_TOKENS` |
| `MAX_STEP_ATTEMPTS` | `3` | попыток исправить один шаг плана |
| `TOKEN_ESTIMATE_DIVISOR` | `3` | делитель запасной оценки `len(text) // N`, когда сервер не вернул `usage`; для кириллического контекста реалистичнее `2` (диапазон `1..16`) |
| `HANDOFF_FILE`, `HANDOFF_BACKUP` | `handoff.md`, `handoff.bak` | файлы состояния механизма Handoff |

Некорректное значение не роняет импорт модуля: в `stderr` пишется
предупреждение, значение заменяется дефолтом.

Для Шага 2 в `.env` важны ровно три первые строки: адрес сервера, ключ и имя
модели. Примеры: LM Studio — `http://localhost:1234/v1`, Ollama —
`http://localhost:11434/v1`, сервер Strata — `http://localhost:8080/v1`.
Ревьюер сам дописывает к адресу путь `/chat/completions`, поэтому `/v1`
указывать нужно, а `/chat/completions` — не нужно.

## Кодировки и пути (важно для Windows)

* `.env` читается как UTF-8 (с BOM и без) и как UTF-16 с BOM — именно его
  даёт `echo "K=v" > .env` в Windows PowerShell 5.1. Файл в другой кодировке
  (например, CP1251) не угадывается: предупреждение в `stderr` и дефолты.
* `.env` ищется сначала в текущем каталоге, затем в каталоге модуля.
  Встроенный парсер `.env` воспроизводит грамматику `python-dotenv`
  (поддерживает комментарии со сдвигом через пробел/таб, пустые значения
  перед комментарием, `export`, кавычки с escape-последовательностями),
  поэтому результат не зависит от наличия или отсутствия необязательной зависимости.
* `stdout` и `stderr` переводятся в UTF-8 в точке входа (`if __name__ == '__main__':`
  и точках входа последующих шагов, согласно правилу 2 PLAN.md). Модуль при импорте
  не меняет глобальное состояние потоков хоста, а функция `_warn()` устойчива к любой
  кодировке `stderr` (включая cp1251/cp437) благодаря безопасному ASCII-фолбэку
  (`backslashreplace`).
* Относительные `HANDOFF_FILE` и `HANDOFF_BACKUP` отсчитываются от каталога
  модуля, а не от текущего каталога процесса: `--resume` найдёт `handoff.md`,
  из какого бы каталога его ни запустили. Файлы `handoff.md` и `handoff.bak`
  включены в `.gitignore`.
* `isolated_reviewer.py` читает и пишет файлы только с явным `encoding="utf-8"`,
  пути держит в `pathlib.Path`, а дочерний процесс компиляции запускает с
  `encoding="utf-8"` и `errors="replace"` — вывод `py_compile` в cp866/cp1251
  не уронит проверку. Проверка синтаксиса ограничена таймаутом 60 секунд,
  запрос к модели — 300 секундами, длинный текст ошибок обрезается, чтобы
  не съедать контекстное окно модели.
* `handoff_manager.py` пишет `handoff.md` в UTF-8 и сразу читает его обратно, чтобы
  убедиться: файл не только записан, но и читается. Чтение терпимо к BOM (`utf-8-sig`),
  а если файл пересохранён в другой кодировке — использует CP1251 как последнее
  средство и обязательно предупреждает об этом. Переименование в `handoff.bak` идёт
  через `Path.replace`, которое на Windows перезаписывает старый `.bak`; при неудаче
  `handoff.md` остаётся на диске — состояние работы не теряется.
* `analyst_planner.py` читает пути `handoff.md` и `handoff.bak` из Шага 1 в момент
  вызова, поэтому относительные пути отсчитываются от папки проекта, а не от текущего
  каталога: `python F:\Projects\team_loop\analyst_planner.py` находит тот же файл,
  из какой бы папки его ни запустили. Восстановление `handoff.md` пишется с явным
  `encoding="utf-8"`. Запрос к модели ограничен таймаутом 300 секунд, а тексты промпта
  обрезаются по длине, чтобы не переполнить контекстное окно.
* `loop_team.py` читает и пишет файлы инструментов только с явным
  `encoding="utf-8"` (при чтении — `errors="replace"`, чтобы файл в чужой кодировке
  не остановил шаг), держит пути в `pathlib.Path` и не выпускает Исполнителя за
  пределы папки проекта. Запрос к модели ограничен таймаутом 600 секунд: Исполнитель
  генерирует целые файлы, и локальная модель на CPU считает медленно. Вывод
  инструментов, отчёт Исполнителя и замечания ревьюера обрезаются по длине, чтобы не
  съесть контекстное окно. UTF-8 включается в консоли только в точке входа.
* `run_strata_team.py` перед `--resume` проверяет, что `handoff.md` или `handoff.bak`
  читаемый и содержит все четыре непустых раздела; проверка не изменяет файлы. Пути
  заданы через `pathlib.Path`, относительные пути отсчитываются от папки проекта.
  UTF-8 в консоли включается самым первым действием — до импорта модулей проекта,
  чтобы русское сообщение о сломанном импорте было читаемым даже в консоли cp866/cp1251.

## Частые проблемы

| Что видно | Причина и решение |
| --- | --- |
| `Проверка модели не выполнена: нет связи с локальным сервером модели` | Сервер модели не запущен или в `.env` указан другой адрес/порт. Запустите сервер модели и сверьте `OPENAI_BASE_URL`. Это **не** ошибка кода: Ревьюер просто не смог спросить модель. |
| `HTTP 400/404` от сервера в тексте `feedback` | Неверный `MODEL_NAME` — модель с таким именем не загружена на сервере. Посмотрите список моделей сервера и поправьте `.env`. |
| `Модель не ответила за 300 секунд` | Модель ещё грузится или отвечает слишком медленно. Повторите запуск, уменьшите размер отчёта Исполнителя, ускорьте инференс. |
| `[ОШИБКА] не найден модуль team_config.py (ШАГ 1)` | `isolated_reviewer.py` лежит не рядом с `team_config.py`. Перенесите его в `F:\Projects\team_loop\`. |
| `Python was not found` или `Не удалось найти` | Windows не видит Python. Попробуйте `py -3 isolated_reviewer.py` либо переустановите Python с галочкой «Add python.exe to PATH». |
| Кириллица в консоли показывается как `?????` | Кодировка консоли не UTF-8. Перед запуском: `chcp 65001`. На файлы и запросы к модели это не влияет — там всегда UTF-8. |
| `.env` не применяется | Проверьте кодировку файла (нужен UTF-8) и не создавайте его через `>` в PowerShell 5.1 — используйте `Copy-Item ".env.example" ".env"`. Уже заданные переменные окружения важнее файла. |
| `Не удалось проверить синтаксис Python` при целом файле | Проблема окружения: нет прав на запись `__pycache__`, файл удерживается редактором или антивирусом, недоступен сетевой диск. Закройте файл/отключите блокировку и повторите. |
| Ревьюер вечно пишет `ДОРАБОТАТЬ` | Так и должно быть, пока цель шага не выполнена: читайте `feedback` — там конкретные правки от модели или текст ошибки компиляции. |
| В консоли `[handoff_manager] Модель не смогла сжать контекст` | Сервер модели выключен или в `.env` неверный адрес. `handoff.md` при этом всё равно создаётся из реальных данных — работа не потеряна. Запустите сервер модели и повторите шаг, чтобы разделы описала модель. |
| В `handoff.md` фраза «собрана программой автоматически» | Это запасной режим Шага 3: модель не ответила или ответ не соответствовал шаблону. Данные в файле настоящие, продолжить работу можно прямо по нему. |
